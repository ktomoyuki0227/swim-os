# Rangers 決済（Stripe）テスト手順書

このドキュメントに沿って操作すれば、月謝・年会費・セッション参加費・Stripe Connect送金まで、決済に関わる主要フローを一通り確認できます。

対象読者: ともくん（開発者本人）。Stripeダッシュボードの操作権限があることを前提にしています。

> **2026-08-22 更新**: 年会費もStripeによるカード自動課金の対象になりました（それまでは現金払いのみ）。月謝と全く同じ仕組み（Stripe Subscription、interval=year）で動くため、シナリオK・L・Mとして月謝(C・D・E)と対になる形でテスト項目を追加しています。

---

## 0. 最初に必ず読んでください（一番重要）

### テストモードでは「本物のカード・本物の銀行口座」は使えない・使う意味がない

今回「自分の銀行口座とクレジットカードを使って試してみたい」とのことでしたが、これは **やらないでください／やる必要がありません**。理由は以下の通りです。

- Stripeのテストモード（サンドボックス）は、本物の金融ネットワーク（カード会社・銀行）に一切接続していません。テスト用のAPIキー（`sk_test_...` / `pk_test_...`）を使っている限り、どんなカード番号・銀行口座番号を入力しても実際の口座からお金が動くことは絶対にありません。
- その代わり、Stripeは「このカード番号を入れると成功する」「この番号を入れると残高不足で失敗する」といった **専用のテスト番号** を用意しています。これを使うことで、実際にお金を動かさずに「決済が成功したときの動き」「失敗したときの動き」を完全に再現できます。
- 逆に、本物のカード番号や本物の銀行口座番号をテストモードの画面に入力すると、Stripe側の形式チェックには通っても実際の口座とは紐付かず、意味のあるテストになりません（クレジットカード会社の規約上も本番以外での実カード番号の使用は推奨されません）。

つまり「本当に引き落とされるか」を確認したいという狙いは、**テスト用カード番号で決済フロー（アプリのDB更新・Webhook・メール通知・Stripe側の請求書発行など）が正しく動くことを確認する**ことで完全に達成できます。実際に本番でお金が動くかどうかは、本番（live）モードのAPIキーに切り替えたときに初めて意味を持つ話であり、それは別の話（かつ実際に課金されるのでテストではなく本番リリースの話）になります。

### 今、テストモードで動いているか必ず確認する

これを確認しないまま進めると「実は本番(live)キーで動いていて、本物のカードを入れたら実際に課金される」という事故につながります。以下のどちらかの方法で必ず確認してください。

1. **Stripeダッシュボード**を開き、右上に「テストモードを表示」のトグルがオンになっているか確認する（オレンジ色の帯や「テストデータ」の表記が出ていればテストモード）。
   https://dashboard.stripe.com/test/dashboard を直接開いても、URLに `/test/` が入っていればテストモードの画面です。
2. アプリの決済系ページ（オンボーディング中のカード登録画面など）で「▼ テストカード（開発用）」というボタンが表示されているか確認する。これは `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY` が `pk_test_` から始まる場合のみ表示されるようにコードで制御されています（`app/(auth)/onboarding/stripe-step.tsx`）。表示されていればテストモードです。

> 補足: 過去のレビュー（`docs/for-reviewer/RELEASE_REVIEW_BRIEF.md`）で「本番運用中のStripeがtest modeとlive modeのどちらのキーで稼働しているか未確認」という指摘が残っています。テストを始める前に、今使っている環境（ローカル / Vercel本番）の `STRIPE_SECRET_KEY` がどちらのキーか、上記の方法で必ず自分の目で確認してください。

## 1. 事前準備

### 1-1. どの環境でテストするか決める

| 環境 | 向いているテスト | 備考 |
|------|----------------|------|
| ローカル（`pnpm dev`） | Webhookの中身を細かく確認したい、コードを直しながら試したい | `stripe listen` でWebhookをlocalhostに転送する必要あり |
| Vercel本番（https://swim-os-seven.vercel.app/） | 実際の利用イメージに近い形で通しで試したい | Webhookは既にStripeダッシュボード側に登録されている想定。Stripeキーがテストモードのものになっているか要確認（上記0章） |

どちらでも手順は同じです。以下はローカルでの手順をベースに書きますが、Vercel環境で試す場合は「1-3. Webhookを受け取れるようにする」だけ読み替えてください。

### 1-2. 使うテスト用アカウントを決める

新しく会員登録してもいいですし、`docs/test-guide.md` に載っている既存のデモアカウントを使っても構いません。

| 役割 | メールアドレス | パスワード | 用途 |
|------|-------------|----------|------|
| コーチ（チーム管理者） | test1@example.com | Delta-coach8820! | チーム作成・Connect設定・開催確定操作 |
| 選手（月謝用） | test2@example.com | Delta-coach8820! | 月謝会員登録・カード登録・セッション参加 |
| 選手（年会費用） | test3@example.com または test4@example.com | Delta-coach8820! | 年会費会員登録・カード登録（月謝の検証結果と混ざらないよう、月謝用とは別アカウントを使う） |

チーム管理者役とは別に、実際にお金を払う側（会員）の役でもう1アカウント用意すると、送金の流れ（会員→プラットフォーム→チーム）がわかりやすくなります。

### 1-3. Webhookを受け取れるようにする（ローカルでテストする場合のみ）

Stripe CLIをインストールしていない場合はインストールしてください。

```bash
# インストール（未導入の場合）
npm install -g @stripe/cli

# ログイン（初回のみ、ブラウザが開く）
stripe login

# Webhookをローカルへ転送（別ターミナルで実行し、テスト中はずっと起動したままにする）
stripe listen --forward-to localhost:3000/api/stripe/webhook
```

`stripe listen` を実行すると `whsec_...` から始まる一時的な署名シークレットが表示されます。これを `.env.local` の `STRIPE_WEBHOOK_SECRET` に設定してから `pnpm dev` を（再）起動してください。これを忘れるとWebhookの署名検証に失敗し、決済は成立してもDBが更新されない（`payment_status` が反映されないなど）状態になります。

Vercel本番で試す場合は、Stripeダッシュボードの「開発者」→「Webhook」で `https://swim-os-seven.vercel.app/api/stripe/webhook` 宛のエンドポイントがテストモードで登録済みか確認してください（登録されていなければ、決済自体は成功してもDB側が更新されません）。

> 古い社内ドキュメント（`docs/MANUAL_OPERATIONS.md`、`docs/browser-setup-guide.md`）には Webhook のURLが `/api/webhooks/stripe` と書かれていますが、これは誤りです。実際の実装は `/api/stripe/webhook` です。今回のテストではこちらの正しいパスを使ってください。

### 1-4. テストで使う番号一覧（ここに出てくる番号は全てStripe公式のテスト専用番号）

**クレジットカード（会員のカード登録・決済用。月謝・年会費どちらにも同じ番号を使います）**

このアプリのカード登録画面には既に主要なテストカードのワンクリックボタンが用意されています（テストモード時のみ表示）。手入力する場合は以下を使ってください。

| 用途 | カード番号 | 有効期限 | セキュリティコード |
|------|----------|--------|------------------|
| 成功する | `4242 4242 4242 4242` | 任意の将来の日付（例: 12/34） | 任意の3桁 |
| 残高不足で失敗 | `4000 0000 0000 9995` | 同上 | 同上 |
| 一般的な拒否で失敗 | `4000 0000 0000 0002` | 同上 | 同上 |
| 有効期限切れで失敗 | `4000 0000 0000 0069` | 同上 | 同上 |

郵便番号の入力欄がある場合は任意の値でOKです。

**Stripe Connect（チームの受け取り口座設定用、日本向け）**

オンボーディング中に本人確認・銀行口座情報の入力を求められますが、以下のテスト専用の値を使います。

| 項目 | 入力する値 | 効果 |
|------|----------|------|
| 生年月日 | `1901-01-01` | 本人確認が即成功する |
| 個人番号（マイナンバー等を聞かれた場合） | `000000000` | 登録番号の照合が成功する |
| 電話番号 | `0000000000` | 電話番号確認が即成功する |
| 銀行口座（銀行コード/支店コード等の「Routing」に相当する欄） | `1100000` | - |
| 口座番号 | `0001234` | 入金（Payout）が成功する口座としてシミュレートされる |
| 本人確認書類のアップロード | アップロードを求められたら、適当な画像ファイルを1枚選択すればOK（テストモードでは内容を見ていない） |
| SMSコード確認 | `000-000` | 電話番号のSMS認証コードとして使う |

住所・氏名・会社名などその他の入力欄は、日本の実在しそうな適当な値（例: 東京都渋谷区1-1-1、郵便番号150-0001）を入れれば通ります。

## 3. シナリオA: Stripe Connectオンボーディング（チームの受け取り設定）

コーチ役（test1@example.com）でログインします。

1. チーム詳細ページを開く（既存チームがなければ「+ チーム作成」から新規作成。作成直後に自動でこのステップに進みます）
2. 決済設定が未完了の場合、チーム詳細ページ上部に警告バナーが表示されます（`stripe-setup-banner.tsx`）。または新規作成直後の画面で「口座情報を登録する」ボタンが表示されます
3. 「口座情報を登録する」を押す → Stripeのホスト型オンボーディング画面に遷移する
4. 「1-4」の表にあるテスト用の値を使って、事業者情報・本人情報・銀行口座情報を入力して進める
5. 最後まで進めると `return_url`（`/api/stripe/connect/callback`）経由でRangersのチーム詳細ページに戻ってくる

### 確認ポイント

- チーム詳細ページの警告バナーが消えていること
- 戻ってきたURLに `connectSuccess=true` が付いていること（アドレスバーで確認）
- Supabaseの `teams` テーブルで該当チームの `stripe_onboarding_completed` が `true`、`stripe_account_id` が `acct_...` の値になっていること
- Stripeダッシュボード（テストモード）の「Connect」→「アカウント」に、今作成したアカウントが `charges_enabled: true` の状態で表示されていること

### つまずきやすい点

- オンボーディング画面を最後まで完了せずに閉じると `stripe_account_id` はあるが `stripe_onboarding_completed` が `false` という「壊れた状態」になります。この状態だと、後述のシナリオF（セッション参加費決済）が `hasBrokenStripeConnect()` のチェックでブロックされます。その場合は再度チーム詳細ページから「口座情報を登録する」を押してオンボーディングを完了させてください。

## 4. シナリオB: 会員のカード登録

選手役（test2@example.com、まだカード未登録のアカウント）でログインします。年会費用の選手役（test3@example.com等）でも同じ手順でカードを登録しておいてください。

**登録場所は2箇所あります（どちらでも同じ結果になります）。**

- 新規登録時のオンボーディング中: `app/(auth)/onboarding/stripe-step.tsx` の画面
- 登録済みアカウントが後からカードを変える場合: 「支払い設定」ページ（`app/(app)/payments/`）の「カード情報を更新」

1. カード登録画面で「▼ テストカード（開発用）」を開く
2. 「4242 4242 4242 4242」（成功）の行をクリック → 即時にカードが登録される

手入力する場合は「1-4」の表のカード番号・任意の有効期限・任意のCVCを入力し、「このカードで登録する」を押します。

### 確認ポイント

- Supabaseの `profiles` テーブルで該当ユーザーの `stripe_customer_id`（`cus_...`）・`stripe_payment_method_id`（`pm_...`）が入っていること
- Stripeダッシュボードの「顧客」に、このユーザーのメールアドレスでCustomerが作成されており、デフォルトの支払い方法が設定されていること

## 5. シナリオC: 月謝（サブスクリプション）の初回課金

前提: シナリオA（チームのConnect設定完了）とシナリオB（会員のカード登録）が終わっていること。また、チーム側で月謝の金額が設定されていること（チーム作成時の料金設定ステップ、または「チーム編集」→会費欄で設定）。

1. 選手役（カード登録済み）で、対象チームに参加する（招待コードでの参加、または会員種別を「月謝」に変更する操作）
2. アプリ内部では `tryStartMonthlySubscription()` が呼ばれ、Stripe Subscription が作成されます（初回のSetup Feeのようなインボイスは `amount_paid=0` としてスキップされる想定）

### 確認ポイント

- Stripeダッシュボードの「サブスクリプション」（テストモード: https://dashboard.stripe.com/test/subscriptions）に、新しいサブスクリプションが `active` で表示されていること
- 少し待つと最初のインボイスが発行され、`invoice.paid` Webhookが発火する（`stripe listen` のログ、またはVercelのログで確認）
- Supabaseの `membership_fees` テーブルに、この会員・このチーム・今月分（`YYYY-MM`）のレコードが1件追加されていること
- `team_members` テーブルの該当行の `subscription_status` が `active` になっていること

### もしサブスクリプションが作成されない場合

`tryStartMonthlySubscription()` は以下のいずれかに該当すると**エラーにせず黙ってスキップ**する仕様です。該当していないか確認してください。

- チームがStripe Connect未設定（シナリオAが未完了）
- 会員がまだカード未登録（シナリオBが未完了）
- 既にアクティブなサブスクリプションがある
- チームに月謝の金額が設定されていない
- 会員種別が「月謝」以外になっている

## 6. シナリオD: 月謝の翌月自動課金（1ヶ月待たずに確認する）

実際に1ヶ月待つ必要はありません。Stripeの「サブスクリプションのシミュレーション」機能で時間を進めます。

1. Stripeダッシュボード（テストモード）で「サブスクリプション」ページを開く: https://dashboard.stripe.com/test/subscriptions
2. シナリオCで作成したサブスクリプションをクリックして詳細を開く
3. ページ上部のバナーにある「シミュレーションを実行」をクリック
4. モーダルで進めたい日時（次回請求日以降）を設定し、「時刻を進める」をクリック
   - 一度に進められるのは最大2請求サイクル分まで（月次サブスクなら最大2ヶ月分）
5. 時刻が進むと、Stripe側で自動的に次回のインボイスが発行・課金される

### 確認ポイント

- サブスクリプション詳細ページの「請求書」欄に、2回目のインボイスが `paid` として追加されていること
- `invoice.paid` Webhookが再度発火し、`membership_fees` テーブルに翌月分（`YYYY-MM` が1ヶ月進んだ値）のレコードが追加されていること
- `stripe_invoice_id` にはUNIQUE制約があるため、同じインボイスに対して重複してレコードが作られていないこと（冪等性の確認）

シミュレーションを終えたら、同じ画面から「シミュレーションを終了」を押すと、テストで作った顧客・サブスクリプションなどがサンドボックスから削除されます（本番環境には影響ありません）。

## 7. シナリオE: 月謝課金の失敗をシミュレートする

カードが使えなくなった場合にアプリがどう反応するかを確認します。

1. Stripeダッシュボードの「顧客」から、シナリオCで使った顧客の支払い方法を、テスト用の「残高不足で失敗するカード」（`4000 0000 0000 9995`）に付け替える
   - もしくは、新しい会員でシナリオB・Cを最初から「1-4」の失敗用カードで登録して試す方法でも構いません
2. シナリオDと同様に「シミュレーションを実行」で次回請求日まで時刻を進める

### 確認ポイント

- `invoice.payment_failed` Webhookが発火すること
- `team_members` テーブルの該当行の `subscription_status` が `past_due` になること
- 管理者・本人に通知（`notifications` テーブル）が作成されていること
- 同じ失敗が2回連続で起きても、通知が重複して量産されないこと（コード上、既に`past_due`なら再通知しない冪等ガードが入っています）

## 8. シナリオF: セッション参加費決済（通常成功パターン）

**重要な仕様**: このアプリでは、セッションに「申し込む」時点では課金されません。課金が実際に走るのは、コーチが「開催確定」ボタンを押したタイミングです（`confirmSession`）。申し込み時点では `payment_status: "pending"` として記録されるだけです。

1. コーチ役で、参加費が発生するセッション（練習会・大会など）を新規作成する
2. 選手役（シナリオBでカード登録済み）で、そのセッションに申し込む。支払い方法の選択肢が出たら「カード（Stripe）」を選ぶ
3. コーチ役に戻り、セッション詳細ページの「開催確定」ボタンを押す
   - 内部的にはここで `chargeSessionRegistrationStripe()` が実行され、PaymentIntentの作成→（Connect設定済みなら送金指定を付けて）confirmが行われます

### 確認ポイント

- 「開催確定しました」というトースト通知が出ること（決済失敗が混在していた場合は「決済失敗N件」という表示になります）
- 選手側の登録状況が `payment_status: "paid"` になっていること（`session_registrations` テーブル）
- Stripeダッシュボード（テストモード）の「決済」に、該当金額のPaymentIntentが `成功` で記録されていること
- チームがConnect設定済みの場合、そのPaymentIntentに送金先（`transfer_data.destination`）が設定されており、`transfer_records` テーブルにも記録が作られていること

## 9. シナリオG: セッション参加費決済の失敗と再試行

1. シナリオFと同じ手順で、選手のデフォルトカードを事前に「1-4」の失敗用カード（`4000 0000 0000 0002` など）に付け替えてから申し込む
2. コーチ役で「開催確定」を押す → 決済失敗が発生し、`payment_status: "failed"` になる
3. セッション詳細ページに「再試行」ボタンが表示されるので押す（`retryPayment`）
   - 失敗の原因（カード）を先にテスト用の成功カードに付け替えてから再試行すると、成功パターンを確認できます

### 確認ポイント

- 失敗時、`payment_status` が `failed` になり管理者にその旨が伝わること
- カードを成功用に付け替えた後の再試行で `payment_status` が `paid` に変わること
- 再試行時、Stripe側で実は既に成功していた決済（PIが`succeeded`）を誤って二重課金しないよう、既存のPaymentIntentの状態を先に確認してからDBだけ同期する動きになっていること（コード上そう実装されています。二重に決済一覧に同じ金額が2件出ていないか確認）

## 10. シナリオH: 現金払いの記録

Stripeを使わずに現金で受け取った場合の管理者操作です。

1. セッションの参加登録時に「現金」を選ぶ（またはコーチが後から現金払いとして記録する）
2. セッション詳細ページの現金管理タブ（`cash-collection.tsx`）で、該当会員の「支払い済みにする」を押す（`markCashPaid`）

### 確認ポイント

- `payment_status` が `paid` になること（Stripeの決済は発生しない）
- 誤って押した場合に「未払いに戻す」（`unmarkCashPaid`）で元に戻せること
- 同時に2人の管理者が同じ会員を操作しても、二重処理にならないこと（内部的に「未払い→支払い済み」という条件付き更新になっているため、後から押した方は「すでに他の操作で更新されています」というエラーになる想定）

## 11. シナリオI: セッション中止時の返金

1. シナリオFで「開催確定」（決済済み）まで進めたセッションを用意する
2. コーチ役でセッションを「中止」する（`cancelSession`）

### 確認ポイント

- 決済済み（`paid`）だった参加者全員に対して自動的にStripe側で返金処理が行われること
- Stripeダッシュボードの該当PaymentIntent/Chargeに「返金済み」の表示が出ること
- Connect送金が発生していた場合、送金も巻き戻される（`reverse_transfer`）こと
- 万が一返金に失敗した参加者がいた場合、セッションの状態が中止前に戻り、再度中止操作をやり直せること

## 13. シナリオK: 年会費（サブスクリプション）の初回課金

シナリオCの年会費版です。2026-08-22の修正で、年会費もカード登録済みの会員に対しては月謝と同じ仕組み（`tryStartAnnualSubscription()`、Stripe Subscription・interval=year）で自動課金されるようになりました。

前提: シナリオA（チームのConnect設定完了）とシナリオB（会員のカード登録）が終わっていること。また、チーム側で年会費の金額が設定されていること（チーム作成時の料金設定ステップ、または「チーム編集」→会費欄で設定）。

1. 選手役（カード登録済み。月謝の検証と混同しないよう、シナリオC〜Eで使ったアカウントとは別にする）で、対象チームに参加する（招待コードでの参加、または会員種別を「年会費」に変更する操作）
2. アプリ内部では `tryStartAnnualSubscription()` が呼ばれ、interval=year のStripe Subscriptionが作成されます

### 確認ポイント

- Stripeダッシュボードの「サブスクリプション」（テストモード: https://dashboard.stripe.com/test/subscriptions）に、新しいサブスクリプションが `active` で表示されていること。詳細を開き、価格の課金間隔が「年次」になっていることを確認する
- 少し待つと最初のインボイスが発行され、`invoice.paid` Webhookが発火する
- Supabaseの `membership_fees` テーブルに、この会員・このチーム・今年分（`type="annual"`、`period` が年のみの4桁、例: `2026`）のレコードが1件追加されていること（月謝(`YYYY-MM`)とは期間のフォーマットが異なる点に注意）
- `team_members` テーブルの該当行の `subscription_status` が `active` になっていること
- Stripeダッシュボードの当該サブスクリプションのmetadataに `fee_type: "annual"` が入っていること（webhookが月謝と年会費を区別するために使っている値）

### もしサブスクリプションが作成されない場合

`tryStartAnnualSubscription()` は以下のいずれかに該当すると**エラーにせず黙ってスキップ**し、代わりに現金払いの年会費レコードが即時作成される仕様です（従来の年会費運用と同じフォールバック）。該当していないか確認してください。

- チームがStripe Connect未設定（シナリオAが未完了）
- 会員がまだカード未登録（シナリオBが未完了）
- 既にアクティブなサブスクリプションがある
- チームに年会費の金額が設定されていない
- 会員種別が「年会費」以外になっている

スキップされた場合、`membership_fees` に `payment_method: "cash"`, `status: "unpaid"` のレコードが即時生成されているはずです（これが今まで通りの年会費のデフォルト挙動）。

## 14. シナリオL: 年会費の翌年自動課金（1年待たずに確認する）

シナリオDの年会費版です。実際に1年待つ必要はありません。同じ「サブスクリプションのシミュレーション」機能で時間を進めます。

1. Stripeダッシュボード（テストモード）で「サブスクリプション」ページを開く: https://dashboard.stripe.com/test/subscriptions
2. シナリオKで作成したサブスクリプションをクリックして詳細を開く
3. ページ上部のバナーにある「シミュレーションを実行」をクリック
4. モーダルで進めたい日時（次回請求日=1年後以降）を設定し、「時刻を進める」をクリック
   - 一度に進められるのは最大2請求サイクル分まで。年次サブスクの場合は最大2年分になるが、1年後を指定すれば十分
5. 時刻が進むと、Stripe側で自動的に次回のインボイスが発行・課金される

### 確認ポイント

- サブスクリプション詳細ページの「請求書」欄に、2回目のインボイスが `paid` として追加されていること
- `invoice.paid` Webhookが再度発火し、`membership_fees` テーブルに翌年分（`period` が1年進んだ4桁の年）のレコードが追加されていること
- `stripe_invoice_id` にはUNIQUE制約があるため、同じインボイスに対して重複してレコードが作られていないこと（冪等性の確認）

シミュレーションを終えたら、同じ画面から「シミュレーションを終了」を押すと、テストで作った顧客・サブスクリプションなどがサンドボックスから削除されます（本番環境には影響ありません）。

## 15. シナリオM: 年会費課金の失敗をシミュレートする

シナリオEの年会費版です。カードが使えなくなった場合にアプリがどう反応するかを確認します。

1. Stripeダッシュボードの「顧客」から、シナリオKで使った顧客の支払い方法を、テスト用の「残高不足で失敗するカード」（`4000 0000 0000 9995`）に付け替える

### 確認ポイント

## 16. テスト後の片付け

- Stripeダッシュボードのテストモードのデータ（顧客・サブスクリプション・PaymentIntent等）は、本番データと別領域（サンドボックス）に保存されているため、放置しても本番に影響しません。気になる場合はテストモード上で個別に削除・キャンセルしてください
- ローカルで `stripe listen` を起動したままにしている場合はテスト終了後に `Ctrl+C` で停止してください
- `.env.local` の `STRIPE_WEBHOOK_SECRET` を `stripe listen` 用の一時シークレットに変更した場合、本番相当の値に戻すのを忘れないようにしてください
