# 新規登録フロー レビュー（2026-08-04）

対象: `/register` → 確認メール → `/register/sent` → `/auth/callback` → `/onboarding`（7ステップ）→ `/dashboard` or `/teams/join/[code]`

コードを実際に読んで確認した内容のみを記載。裏取りできていない推測は「要検証」と明記した。

---

## HIGH

### 1. 確認メールが無効/期限切れの場合、ユーザーに何も説明されない

- `app/auth/callback/route.ts:10-18`
- 確認リンクをクリックした際に `exchangeCodeForSession` が失敗すると（リンクが期限切れ・既に使用済みなど）、`/login?error=auth` にリダイレクトされる。
- しかし `app/(auth)/login/page.tsx` は `searchParams` の `error` を一切読んでおらず、表示もしていない。
- **結果**: ユーザーは何の説明もなく普通のログイン画面に飛ばされるだけ。メール確認が失敗したことにも気づけず、再登録・再送信の導線もない。数日後にメールを確認するようなユーザーほど踏みやすい。

**対応案**: `login/page.tsx` で `error=auth` を検出し、「確認リンクの期限が切れています。もう一度登録するか、確認メールを再送信してください」等のメッセージ＋導線を表示する。

## MEDIUM–HIGH

### 2. パスワードの入力ヒントと実際のバリデーションが矛盾している

- `app/(auth)/register/page.tsx:111-119`: `minLength={6}` / placeholder「6文字以上」
- `lib/validations.ts:23`: `registerSchema` は `z.string().min(8, "パスワードは8文字以上で入力してください")`
- **結果**: 6〜7文字のパスワードはブラウザ側のバリデーションを通過して送信されるが、サーバー側で弾かれ「8文字以上」というヒントと矛盾したエラーが表示される。ユーザーからすると「言われた通り6文字で入れたのに怒られた」という体験になる。

**対応案**: `minLength` と placeholder を `8` に合わせる（もしくはスキーマ側を6に緩めるが、他のパスワード関連バリデーションとの整合性を優先するなら表示側を8に統一するのが妥当）。

### 3. オンボーディング（7ステップ）の入力内容がどこにも保存されず、離脱で全消去される

- `app/(auth)/onboarding/page.tsx:83-88`: `step` / `swimmerForm` / `personalForm` はすべてクライアント側の `useState` のみで保持。
- サーバーへの保存は最終ステップの `handleComplete()` 一発でしか行われない（`actions/onboarding.ts` の `completeOnboarding`）。
- **結果**: 写真アップロード・基本情報・緊急連絡先・競技登録・カード情報入力という長いフローの途中で、誤ってブラウザを閉じる／リロードする／戻るボタンを押す／回線が不安定なモバイルでタブが再読み込みされる、といった操作をすると入力内容が全て失われ最初からやり直しになる。離脱を防ぐ `beforeunload` 警告もない。
- DESIGN.md 上のメインターゲット（50〜60代）を踏まえると、離脱率に直結しやすい箇所。

**対応案**: 最低限、各ステップ完了時に `localStorage`（または下書きとしてDB）に一時保存し、リロード後に復元できるようにする。

### 4. Step 1 でプロフィール写真が必須になっており、スキップできない

- `app/(auth)/onboarding/swimmer-profile-step.tsx:74-77`（「プロフィール写真（必須）」）
- `app/(auth)/onboarding/page.tsx:93-98`: `step1Valid` は `avatarFile` 必須 + レベル必須 + 種目1つ以上 + 目的1つ以上 + 都道府県1つ以上をすべて満たさないと「次へ」が押せない。
- 一方 Step 6（お支払い）だけは「スキップ」ボタンがあるのに、Step 1〜5にはスキップ手段が一切ない。
- **結果**: 登録直後に手元に写真がない・写真をまだ用意したくないユーザーは、その場でオンボーディングを止められてしまう。

**対応案**: 写真を任意項目にする（プレースホルダー画像で代替）か、後からプロフィールページで設定できる旨を明記して先に進めるようにする。

## MEDIUM

### 5. `/register/sent` にメールアドレスを訂正する導線がない

- `app/(auth)/register/sent/page.tsx` / `resend-confirmation-form.tsx`
- できるのは「同じアドレスへの再送信」か「ログインページへ」のみ。
- **結果**: 登録時にメールアドレスをタイプミスしたユーザーは、間違ったアドレスに何度再送信しても永遠にメールが届かない。しかも他に導線がないため「なぜ届かないのか」に気づく手段がない。

**対応案**: 「メールアドレスを間違えた場合は」→ 新規登録画面へ戻るリンクを追加する（別アドレスで再登録すれば、未確認の古いアカウントとは独立して進められる）。

### 6. 確認メール未着時の案内に記載された送信元アドレスが実際と一致していない可能性

- `app/(auth)/register/sent/page.tsx:70`: 「`noreply@rangers.jp` からのメールが届くよう設定をご確認ください」と固定表示。
- リポジトリ内に SMTP 関連の環境変数・設定が見当たらず（`.env.local.example` にも記載なし）、カスタムSMTP（独自ドメイン送信）を設定している形跡がコード上では確認できなかった。
- **結果（要検証）**: Supabaseプロジェクトの Authentication → SMTP Settings でカスタムSMTP＋ `rangers.jp` ドメインの送信者を設定済みであれば問題ないが、未設定の場合は実際の送信元が Supabase 標準ドメイン（`*.supabase.co` 系）になり、案内文の送信元と食い違う。ユーザーが案内通りに `rangers.jp` だけを許可リストに入れると、かえって実際のメールが届かない・迷惑メール判定される恐れがある。

**対応案**: Supabaseダッシュボードの SMTP 設定を確認し、実際の送信元アドレスに文言を合わせる。

## LOW

### 7. 使われていない `/register/confirm` ページが残っている

- `app/(auth)/register/confirm/page.tsx`
- コードベース全体を検索したが、このパスへのリンクは一切存在しない（実際のフローは `register()` アクションが `/register/sent` にリダイレクトする実装になっている）。
- 内容も現行のブランディングと食い違っている（フッター文言が「マスターズ水泳レッスン予約」＝旧コピー。現行は login ページ等で「マスターズ水泳グループ管理」に統一済み）。
- URLを直接叩けば誰でも到達できてしまうため、古い文言のまま残るのは望ましくない。

**対応案**: 未使用であれば削除。使う予定があるなら文言を現行ブランディングに合わせる。

### 8. レート制限がインスタンスローカル（既知のトレードオフ、要注意事項として記載）

- `lib/rate-limit.ts:8-11` にコメントの通り、メモリ内Mapで実装されておりインスタンスをまたいだ分散カウントにはならない。実装者はこれを認識した上での意図的なトレードオフとして明記済み。
- 登録・再送信・パスワードリセットのレート制限がこの仕組みに依存しているため、複数インスタンスに散った場合は実際の上限が緩くなる（例: 5回/時間の想定が、インスタンス数倍まで緩和されうる）。
- 現状は許容範囲内の判断だが、悪用が増えた場合はUpstash Ratelimit等への切り替えを検討する必要がある（コード内コメントにも同様の記載あり）。

## 確認できた「問題なし」の項目（念のため記載）

- オンボーディング完了済みユーザーが `/onboarding` に再訪すると `/dashboard` へリダイレクトされる（`onboarding/layout.tsx:25-27`）。ループや二重送信のリスクなし。
- 未ログインユーザーが `/dashboard` 等の保護ページへ行くと `/login` へリダイレクトされる（`(app)/layout.tsx:18-20`）。
- プロフィール未作成（不整合）ユーザーは自動サインアウト後 `/login` に戻される（`(app)/layout.tsx:33-37`）。
- 招待コード経由の登録（`/teams/join/[code]` → `/register?invite=`）は、招待コードの有効性を **オンボーディング開始前** に検証済み。無効な招待で長い登録フローを完走させられることはない。
- `next` パラメータは `safeRedirectPath()` でオープンリダイレクト対策済み（外部ドメイン・プロトコル相対URLを拒否）。
- パスワード再設定・確認メール本文は日本語化済み（本セッションで対応）。

## 対応状況（2026-08-04）

上記1〜8すべて対応済み。加えて、レビュー後にユーザーから指摘のあった「新規登録・オンボーディングと確認メール画面でステップ表示の尺度が異なり紛らわしい」問題も合わせて修正した。

- #1: `login/page.tsx` で `?error=auth` を検出し、期限切れ・使用済みリンクの案内＋再登録導線を表示
- ステップ表示統一: `app/(auth)/step-progress.tsx` に「アカウント作成→メール確認→自己紹介→…→お支払い」の8ステップを一本化し、register・register/sent・onboardingの3ページで共有
- #2: `register/page.tsx` のパスワードヒントを8文字以上に統一（`registerSchema` と整合）
- #3: オンボーディングの入力内容を `localStorage` に自動保存し、リロード後も復元（`app/(auth)/onboarding/draft.ts`）。avatarFileはdata URL経由で完全復元
- #4: Step1のプロフィール写真を任意化（DB側も元々NOT NULL制約なし）
- #5, #6: `register/sent` の「noreply@rangers.jp」という検証していない送信元表記を削除し、代わりに登録やり直し導線を追加（両問題を同時に解消）
- #7: 未使用の `app/(auth)/register/confirm/` を削除

`npx tsc --noEmit` / `npx eslint` とも問題なし。
