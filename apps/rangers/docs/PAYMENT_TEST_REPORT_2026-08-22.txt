================================================================================
 Rangers 決済(Stripe)機能 テスト・レビュー 総合報告
 作成日: 2026-08-22 / 最終更新日: 2026-08-26
================================================================================

本書は、Rangers(スイミングチーム管理アプリ)の決済(Stripe)機能について実施
したレビュー・自動テスト・不具合修正の内容をまとめたものです。エンジニアの
方に本アプリのレビューを依頼するにあたり、決済まわりで既に確認・対応済みの
内容を正確に共有することを目的としています。


================================================================================
 サマリー(まずここだけ読めば全体像がわかります)
================================================================================

【対応した内容】
決済に関わるコード全体をレビューし、実際にお金が正しく動くかを実機で検証する
過程で、合計7件の不具合(うち5件は「決済が発生しない/記録されない/検知され
ない」という重大なもの)を発見し、すべて修正・再検証済みです。年会費のカード
自動課金も新規に実装し、月謝と同水準までテストしています。

【現在の状態】
決済に関わる主要シナリオ(月謝・年会費の初回課金/更新課金/課金失敗、セッション
参加費のカード決済/回数券決済/現金決済/返金/再試行、Stripe Connectでの送金
分配、会費金額変更時の追従)について、実際にStripeのテスト環境上でお金が
動く形で一通り検証し、問題がないことを確認しています。コード上で見つけられる
範囲の不具合は出し切ったという認識です。

【まだ済んでいないこと(いずれも「実際に本番課金へ切り替える段階」で対応すれば
よく、現時点でブロッカーにはなりません)】
  ・本番用Stripe APIキーがVercelのProduction環境変数に設定されているかの確認
  ・Stripeをライブモードに切り替えた状態でのWebhookエンドポイント登録
(詳細は本書末尾「今後の対応(本番切り替え時)」を参照してください)

【本書のスコープ外】
今回の対応は決済(Stripe)機能に特化しています。認証・権限管理・RLS・
アクセシビリティ等、決済以外の領域は本書の対象外です(過去の別セッションで
複数回レビュー済みですが、本書には含めていません)。


================================================================================
 本書の読み方・テスト環境について
================================================================================

【テストの実施方法】
Stripeが提供する「テストモード」(実際の資金移動が一切発生しない検証用の
環境)上で、Playwright(ブラウザ自動操作ツール)によるヘッドレスブラウザ
テストスクリプトを作成し、実際のログイン → 画面操作 → 決済実行 → 結果確認
という一連の流れを人手を介さず検証しました。テストカードには実在しない
Stripe公式のテスト用カード番号を使用しています。

重要な補足として、これらは CI(継続的インテグレーション)に組み込まれた
自動テストスイートではなく、`node scripts/test-xxx.mjs` の形で都度手動実行
するスクリプト群です。プロジェクトの `scripts/` ディレクトリに残してあり、
今後の機能変更時の回帰確認にはそのまま再利用できますが、リポジトリへの
プッシュ時に自動で走るような仕組みにはなっていません。

【テスト環境について】
今回のテストは、実際に稼働している本番のSupabaseデータベース上で、あらかじめ
用意されているデモ用アカウント(test1〜test4等のダミーメールアドレス)を使って
実施しました。別途隔離されたstaging環境ではありません。ただし、Stripe側は
一貫してテストモードのAPIキーを使用しているため、実際のクレジットカードへの
課金や銀行口座への入出金は一切発生していません。テストで変更した会員種別・
カード登録状態・会費金額等はすべて元の状態へ復元済みです。テスト用に作成した
セッションのうち決済履歴が残るもの(3件)は、アプリ自体の設計(決済記録が
残るセッションは削除できない仕様)により物理的な削除はできないため、「中止・
返金済み」の状態のまま残っています。実運用データへの影響はありません。

【検証環境のバージョン情報】
Next.js 16 (App Router) / React 19 / TypeScript / Supabase (Postgres) /
Stripe SDK(Subscriptions・PaymentIntents・Connect・Webhooks)

================================================================================
 発見・修正した不具合一覧(重要度順)
================================================================================

--------------------------------------------------------------------------------
【重大】月謝Subscriptionの初回課金が一度も実行されていなかった
--------------------------------------------------------------------------------
Stripeの仕様上、サブスクリプション作成直後の初回請求は「明示的に確定処理を
呼び出さない限り自動では課金されない」仕様でした。この確定処理が実装から
漏れており、月謝会員のサブスクリプションは作成されるだけで、カードへ一度も
課金されていませんでした。→ 確定処理を追加し修正済み。

--------------------------------------------------------------------------------
【重大】2年目以降の会費(更新分)がデータベースに一切記録されない
--------------------------------------------------------------------------------
Stripeの「今回の請求期間の開始時刻」は、2回目以降の請求ではSubscription
作成時点のまま固定される仕様があり、この値をそのまま使って支払い年月を
計算していたため、2年目の年会費・2ヶ月目以降の月謝がすべて「初回と同じ
期間」として記録されようとし、一意制約に阻まれて記録が作られませんでした。
決済自体は成功しているのに、会費一覧・通帳に反映されない状態でした。
→ 請求サイクルの開始時刻をインボイスの明細行から正しく取得するよう修正。
  Test Clockで1年後・2年後まで実際に時間を進めて修正を確認済み。

--------------------------------------------------------------------------------
【重大】セッション参加費のカード決済が常に失敗する
--------------------------------------------------------------------------------
Stripeへの決済リクエストの組み立て方に誤りがあり、決済リクエスト自体が必ず
エラーになっていました。このエラーが記録に残らない形で握りつぶされていた
ため、「参加登録はできるが、実際にはカードへの請求が一度も成功しない」状態
に気づかれずに続いていました(現金払い運用では発生しない問題でした)。
→ リクエストの組み立て方を修正し、エラー時はログに残るよう修正済み。

--------------------------------------------------------------------------------
【重大】初回課金の失敗が誰にも気づかれず、永久に未収のままになる
--------------------------------------------------------------------------------
初回課金の確定処理自体が失敗した場合(無効化されたカード等)、通常の更新課金
失敗とは異なりStripe側の失敗通知(Webhook)が一切発生しない仕様でした。この
失敗を検知する処理がなく、失敗した会員のSubscriptionは「未完了」のまま放置
され、「Stripe側がいずれ処理してくれるはず」という既存の判定ロジックに引っ
かかり、現金払いへの切り替えフォールバックの対象からも外れ、本人・管理者
ともに一切気づけないまま会費が永久に未収となる状態でした。
→ 失敗検知時にSubscriptionを明示的にキャンセルして正しく「未収」の終端状態
  に戻し、現金払いフォールバックに委ねると同時に、本人・管理者へ通知するよう
  修正済み。

--------------------------------------------------------------------------------
【重大】外部公開セッションでゲスト(非会員)が常に参加登録できない
--------------------------------------------------------------------------------
「外部公開する(メンバー以外も参加可能)」を有効にしたセッションでも、作成
時の「配信対象」項目がデフォルトで「現在の全メンバーを選択」状態になって
おり、この選択リストが参加登録の可否判定にも使われていたため、メンバーで
ないゲストは仕組み上絶対にこのリストに含まれず、常に参加登録を拒否されて
いました。画面上は「参加できます」と表示されるのに、実際には必ず失敗する
状態で、「メンバー以外も参加可能」機能が実質的に一度も機能していませんでした。
→ 対象メンバーによる絞り込みを会員のみに適用するよう修正(ゲストには適用
  しない)。既存の「特定メンバーだけに公開する」機能への影響はなし。

--------------------------------------------------------------------------------
【軽微】セッション詳細画面で管理者専用ボタンが一般メンバーにも見えていた
--------------------------------------------------------------------------------
開催確定・中止・削除・現金集金などの管理操作ボタンが、権限のない一般メンバー
の画面にも表示されていました。クリックしても裏側の処理では正しく権限拒否
される作りだったため実害はありませんでしたが、表示を管理者のみに限定する
よう修正しました。

--------------------------------------------------------------------------------
【インフラ】本番URLに設定ミスの古いStripe Webhookエンドポイントが残っていた
--------------------------------------------------------------------------------
本番環境の実行ログを確認したところ、設定時タイプミスの古いWebhookエンド
ポイント(2026年5月作成)が5分間隔程度で404エラーを出し続けていました。
実際に使われている正しいエンドポイント(2026年6月作成)は別途正常に機能して
いたため決済処理そのものへの実害はありませんでしたが、放置するとStripe側の
配信失敗率の指標を無駄に悪化させ、本当の障害時にノイズに紛れて気づきにくく
なるため削除しました。

--------------------------------------------------------------------------------
【着手前レビューで発見・修正済みの項目(年会費対応着手前)】
--------------------------------------------------------------------------------
上記の実機テストに着手する前段として、決済に関わる既存コード全体を静的に
レビューし、以下を修正済みです。
  ・会員のStripe顧客ID・支払い方法ID・チームの受け取り口座IDが、管理者権限
    を持たない操作から書き換えられないようDB側で保護
  ・セッション・参加申込等の削除時に、連動して会費・決済履歴まで自動削除
    されてしまう設定を修正(履歴が残るように変更)
  ・現金払いの会費を「支払い済み」にする操作の二重処理防止(原子的な更新に)
  ・Stripe Webhook処理でエラーが発生しても正常応答を返してしまい、実際には
    課金されているのに記録が残らない状況になり得た実装を修正(エラー時は
    再送を促すよう変更)
  ・Stripeの秘密鍵を扱うコードがブラウザ向けコードに混入しないよう保護を追加
  ・個人レッスン予約・決済のための未使用の旧機能一式を削除

 正常動作を確認した項目(不具合なし)
================================================================================

上記の不具合修正の過程・その後の追加検証で、以下は正しく動作することを
確認済みです。

  ・回数券(point_card)払いでのセッション参加費決済とスタンプ消費・通知
  ・Stripe Connectアカウント作成済みだがオンボーディング未完了のチームで、
    決済が正しくブロックされる(送金先不明の誤課金を防ぐ安全装置)
  ・Stripe Connect未設定チームでのゲスト参加費のカード決済(送金分配なし・
    全額プラットフォーム残高)
  ・決済失敗からの再試行、現金払いの集金記録・取消、セッション中止時の
    自動返金・送金巻き戻し
  ・チームが会費金額を後から値上げ/値下げした際、未加入会員への新規
    Subscription遡及開始と、既存加入会員への価格追従(月謝・年会費両方)
  ・管理者がメンバーを削除した場合、会員種別を月謝/年会費から変更した場合の
    Stripe Subscription解約の連動
  ・Stripe Connectオンボーディング本体(手動確認。ボット検知認証のため
    自動化は不可と判断し、実際の操作で完了を確認)


================================================================================
 今後の対応(本番切り替え時)
================================================================================

以下2点は、実際に本番(ライブモード)課金へ切り替えるタイミングで確認が
必要です。テストモードでの確認だけではカバーできない項目のため、現時点では
未確認のままですが、本番移行の判断自体を妨げるものではありません。

  1. 本番用のStripe APIキー(STRIPE_SECRET_KEY等)が、Vercelの Production
     環境変数に正しく設定されていること
  2. 本番用Webhookエンドポイント(https://<本番ドメイン>/api/stripe/webhook)
     が、Stripeダッシュボードをライブモードに切り替えた状態で登録されて
     いること(テストモードには既に正しく登録済み・タイプミスで壊れていた
     古いエンドポイントは削除済み)

なお、Connect(チームの受け取り口座)の本人確認は、テストモードと本番
(ライブ)モードで完全に別のアカウント・別の審査になるため、本番移行時は
各チームの管理者が改めて実際の本人確認書類でオンボーディングを行うことに
なります。これは通常の運用開始フローであり、今回のテストとは独立した対応
です。

今回作成した自動テストスクリプト(scripts/test-*.mjs、実行完了済み15本)は
プロジェクトに残してあるため、今後の機能変更時の回帰確認にそのまま再利用
できます。
